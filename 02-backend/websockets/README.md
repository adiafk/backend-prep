# WebSockets

## 1. WebSocket vs HTTP — When to Use Each

### HTTP Request-Response
HTTP is stateless and follows a request-response model. The client initiates every exchange; the server cannot push data unprompted.

**Use HTTP when:**
- Data changes infrequently (product catalog, user profile)
- Client drives all interaction (form submissions, CRUD)
- Caching is important (CDN, browser cache)
- You need simple fire-and-forget semantics
- REST or GraphQL query/mutation patterns fit naturally

### Server-Sent Events (SSE)
One-way, server-to-client streaming over a persistent HTTP connection. Simpler than WebSockets but unidirectional.

**Use SSE when:**
- Server pushes updates to client only (live scores, log tails, AI token streaming)
- You want automatic reconnection built into the browser
- Firewall/proxy compatibility matters (it is plain HTTP)

### WebSockets
Full-duplex, persistent TCP connection. After a one-time HTTP upgrade, both sides send frames freely.

**Use WebSockets when:**
- Bidirectional, low-latency communication is required (chat, collaborative editing, multiplayer games)
- High message frequency makes polling expensive
- You need sub-100 ms latency
- The server must push data at arbitrary times AND the client sends responses back

### Decision matrix

| Criterion | HTTP polling | SSE | WebSocket |
|---|---|---|---|
| Direction | Client pulls | Server pushes | Both directions |
| Latency | High (poll interval) | Low | Very low |
| Overhead per message | High (full headers) | Low | Very low (2-byte frame header) |
| Browser reconnect | Manual | Automatic | Manual |
| Proxy/firewall friendly | Yes | Yes | Sometimes requires config |
| Server complexity | Low | Low | Medium-High |

## 2. WebSocket Handshake — How the Upgrade Works

WebSocket connections begin as a normal HTTP/1.1 request. The client sends an `Upgrade` header asking the server to switch protocols.

### Step 1 — Client sends HTTP upgrade request

```
GET /ws HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Sec-WebSocket-Protocol: chat, superchat   (optional subprotocol negotiation)
Sec-WebSocket-Extensions: permessage-deflate  (optional)
```

`Sec-WebSocket-Key` is a base64-encoded random 16-byte nonce generated by the client. It is not a security mechanism — it prevents caching proxies from replaying responses.

### Step 2 — Server responds with 101 Switching Protocols

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: chat
```

`Sec-WebSocket-Accept` is computed as:

```
base64( SHA1( clientKey + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )
```

The magic GUID `258EAFA5...` is defined in RFC 6455. This prevents non-WebSocket servers from accidentally accepting upgrade requests.

### Step 3 — TCP connection is now a WebSocket

After the 101, the underlying TCP socket is handed off. HTTP parsing stops. Both sides communicate using the WebSocket framing protocol — small binary frames with a 2–10 byte header containing opcode, masking bit, and payload length.

**Key frame opcodes:**
- `0x1` — text frame (UTF-8)
- `0x2` — binary frame
- `0x8` — close
- `0x9` — ping
- `0xA` — pong

Client-to-server frames are always masked (XOR with a 4-byte masking key). Server-to-client frames are unmasked.

## 3. Events — open, message, close, error

### Browser WebSocket API

```typescript
const ws = new WebSocket('wss://example.com/ws');

// Connection established — handshake complete
ws.addEventListener('open', (event) => {
  console.log('Connected');
  ws.send(JSON.stringify({ type: 'subscribe', channel: 'prices' }));
});

// Message received from server
ws.addEventListener('message', (event: MessageEvent) => {
  const data = JSON.parse(event.data as string);
  console.log('Received:', data);
});

// Connection closed — either side can initiate
ws.addEventListener('close', (event: CloseEvent) => {
  // event.code: numeric close code (1000 = normal, 1006 = abnormal)
  // event.reason: human-readable string
  // event.wasClean: boolean
  console.log(`Closed: code=${event.code} reason=${event.reason} clean=${event.wasClean}`);
});

// Network or protocol error — always followed by a close event
ws.addEventListener('error', (event: Event) => {
  console.error('WebSocket error', event);
  // Note: browser error events carry no useful detail for security reasons
});
```

### Common close codes (RFC 6455)

| Code | Meaning |
|---|---|
| 1000 | Normal closure |
| 1001 | Going away (browser navigating away) |
| 1002 | Protocol error |
| 1003 | Unsupported data type |
| 1006 | Abnormal closure (no close frame received) |
| 1008 | Policy violation |
| 1011 | Server internal error |
| 4000–4999 | Application-defined codes |

## 4. Scaling WebSockets — Sticky Sessions and Redis Pub/Sub

### The scaling problem

WebSocket connections are stateful and long-lived. With a single server this is trivial — broadcast means iterating over all connected sockets. With multiple server instances, a message received by instance A needs to reach clients connected to instances B and C.

### Option 1 — Sticky sessions (L4/L7 load balancer)

Configure the load balancer to route all requests from a given client to the same server instance, based on IP hash or a session cookie.

**Pros:** Simple, no extra infrastructure.

**Cons:**
- Instance failure drops all its connections simultaneously (thundering herd on reconnect)
- Uneven load distribution if clients have different activity levels
- Does not solve cross-instance broadcast — instance A still cannot talk to clients on B

**Nginx example:**
```nginx
upstream websocket_servers {
    ip_hash;   # sticky by client IP
    server ws1:3000;
    server ws2:3000;
    server ws3:3000;
}
```

### Option 2 — Redis Pub/Sub (recommended for broadcast)

Each server instance subscribes to Redis channels. When any instance receives a message that needs broadcasting, it publishes to Redis. All instances receive it and forward to their local clients.

```
Client A → Instance 1 → publish("room:42", msg) → Redis
                                                      ↓
Instance 1 ← subscribe("room:42") ← Redis → Instance 2 ← subscribe("room:42")
     ↓                                              ↓
  Client A                                       Client B
```

```typescript
import { createClient } from 'redis';
import { WebSocketServer, WebSocket } from 'ws';

const pub = createClient({ url: 'redis://localhost:6379' });
const sub = createClient({ url: 'redis://localhost:6379' });

await pub.connect();
await sub.connect();

const wss = new WebSocketServer({ port: 3000 });
const localClients = new Map<string, WebSocket>();

// Subscribe to the broadcast channel on Redis
await sub.subscribe('broadcast', (message) => {
  // Fan out to all clients connected to THIS instance
  for (const ws of localClients.values()) {
    if (ws.readyState === WebSocket.OPEN) {
      ws.send(message);
    }
  }
});

wss.on('connection', (ws, req) => {
  const clientId = crypto.randomUUID();
  localClients.set(clientId, ws);

  ws.on('message', async (data) => {
    // Publish to Redis — all instances will fan out to their clients
    await pub.publish('broadcast', data.toString());
  });

  ws.on('close', () => localClients.delete(clientId));
});
```

### Option 3 — Socket.IO with Redis adapter

Socket.IO's `@socket.io/redis-adapter` handles the pub/sub wiring automatically and adds room semantics, making per-room broadcasts straightforward.

## 5. Heartbeat / Ping-Pong — Why Needed and How to Implement

### Why heartbeats are necessary

TCP connections can silently die. Intermediate proxies (AWS ALB, Nginx, corporate firewalls) terminate idle TCP connections — often after 60–120 seconds of inactivity. Neither side receives a close event; the connection appears open but is actually dead (a "half-open" connection). Without a heartbeat, the server accumulates zombie connections, and clients do not know they need to reconnect.

### WebSocket ping-pong (RFC 6455 frames)

The protocol defines ping (`0x9`) and pong (`0xA`) control frames. The server sends a ping; the client must respond with a pong containing the same payload. The `ws` library handles this at the framing layer.

### Server-side implementation

```typescript
import { WebSocketServer, WebSocket } from 'ws';

const HEARTBEAT_INTERVAL_MS = 30_000;
const HEARTBEAT_TIMEOUT_MS  = 10_000;

interface ExtWebSocket extends WebSocket {
  isAlive: boolean;
  pingTimeout?: ReturnType<typeof setTimeout>;
}

const wss = new WebSocketServer({ port: 3000 });

function heartbeat(this: ExtWebSocket) {
  // Called when a pong is received — client is alive
  this.isAlive = true;
  clearTimeout(this.pingTimeout);
}

wss.on('connection', (ws: ExtWebSocket) => {
  ws.isAlive = true;
  ws.on('pong', heartbeat.bind(ws)); // ws fires 'pong' automatically on receipt

  ws.on('close', () => clearTimeout(ws.pingTimeout));
});

// Interval: ping all connected clients
const interval = setInterval(() => {
  wss.clients.forEach((rawWs) => {
    const ws = rawWs as ExtWebSocket;

    if (!ws.isAlive) {
      // No pong received since last ping — terminate
      ws.terminate();
      return;
    }

    ws.isAlive = false;
    ws.ping(); // send RFC 6455 ping frame

    // Optional: hard deadline if pong does not arrive
    ws.pingTimeout = setTimeout(() => {
      ws.terminate();
    }, HEARTBEAT_TIMEOUT_MS);
  });
}, HEARTBEAT_INTERVAL_MS);

wss.on('close', () => clearInterval(interval));
```

### Application-level heartbeat (alternative)

Some clients (browser WebSocket API) do not expose the raw pong event. In that case, implement heartbeat at the application layer:

```typescript
// Server sends a JSON ping every 30 s
ws.on('open', () => {
  const timer = setInterval(() => ws.send(JSON.stringify({ type: 'ping' })), 30_000);
  ws.on('close', () => clearInterval(timer));
});

// Client replies
ws.on('message', (data) => {
  const msg = JSON.parse(data.toString());
  if (msg.type === 'ping') ws.send(JSON.stringify({ type: 'pong' }));
});
```

## 6. Authentication with WebSockets

HTTP cookies are sent automatically on WebSocket upgrade requests to the same origin, making cookie-based sessions the simplest approach. For token-based auth, two common patterns exist.

### Option A — Token in query parameter (simple, has trade-offs)

```
wss://example.com/ws?token=eyJhbGciOiJIUzI1NiJ9...
```

**Pros:** Works in all environments; token available before the connection is accepted.

**Cons:**
- Token appears in server access logs, browser history, and Referer headers — treat as a short-lived token only
- Some proxies log query strings

```typescript
import { parse } from 'url';
import jwt from 'jsonwebtoken';

wss.on('connection', (ws, req) => {
  const { query } = parse(req.url ?? '', true);
  const token = query.token as string | undefined;

  if (!token) {
    ws.close(4001, 'Authentication required');
    return;
  }

  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET!);
    (ws as any).user = payload;
  } catch {
    ws.close(4002, 'Invalid token');
  }
});
```

### Option B — Token in first message (preferred for long-lived tokens)

Accept the connection but treat it as unauthenticated until the client sends an auth message within a timeout window.

```typescript
const AUTH_TIMEOUT_MS = 5_000;

wss.on('connection', (ws: ExtWebSocket) => {
  let authenticated = false;

  // Give the client 5 s to authenticate
  const authTimeout = setTimeout(() => {
    if (!authenticated) ws.close(4001, 'Authentication timeout');
  }, AUTH_TIMEOUT_MS);

  ws.on('message', (data) => {
    const msg = JSON.parse(data.toString());

    if (!authenticated) {
      if (msg.type !== 'auth') {
        ws.close(4003, 'Expected auth message');
        return;
      }

      try {
        const payload = jwt.verify(msg.token, process.env.JWT_SECRET!);
        (ws as any).user = payload;
        authenticated = true;
        clearTimeout(authTimeout);
        ws.send(JSON.stringify({ type: 'auth_ok' }));
      } catch {
        ws.close(4002, 'Invalid token');
      }
      return;
    }

    // Handle normal messages after auth
    handleMessage(ws, msg);
  });

  ws.on('close', () => clearTimeout(authTimeout));
});
```

### Token refresh

JWTs expire. Send the new token via an application-level message before expiry; the server updates the stored user context without dropping the connection.

## 7. Reconnection Strategies — Exponential Backoff

### Why reconnection is necessary

Networks are unreliable. Servers restart for deployments. Load balancers drain connections. A robust client must reconnect automatically without hammering the server.

### Exponential backoff with jitter

```typescript
interface ReconnectOptions {
  url: string;
  onMessage: (data: unknown) => void;
  initialDelayMs?: number;
  maxDelayMs?: number;
  maxAttempts?: number;
}

function createReconnectingWebSocket(opts: ReconnectOptions) {
  const {
    url,
    onMessage,
    initialDelayMs = 1_000,
    maxDelayMs = 30_000,
    maxAttempts = Infinity,
  } = opts;

  let ws: WebSocket | null = null;
  let attempt = 0;
  let stopped = false;

  function connect() {
    if (stopped) return;

    ws = new WebSocket(url);

    ws.addEventListener('open', () => {
      console.log(`Connected (attempt ${attempt})`);
      attempt = 0; // reset backoff on successful connection
    });

    ws.addEventListener('message', (event: MessageEvent) => {
      try {
        onMessage(JSON.parse(event.data as string));
      } catch {
        onMessage(event.data);
      }
    });

    ws.addEventListener('close', (event: CloseEvent) => {
      if (stopped) return;
      if (event.code === 1000) return; // clean close — do not reconnect

      attempt++;
      if (attempt > maxAttempts) {
        console.error('Max reconnect attempts reached');
        return;
      }

      const baseDelay = Math.min(initialDelayMs * 2 ** (attempt - 1), maxDelayMs);
      // Add jitter: random value in [0, baseDelay * 0.3]
      // Jitter prevents all clients from reconnecting simultaneously (thundering herd)
      const jitter = Math.random() * baseDelay * 0.3;
      const delay = baseDelay + jitter;

      console.log(`Reconnecting in ${Math.round(delay)}ms (attempt ${attempt})`);
      setTimeout(connect, delay);
    });

    ws.addEventListener('error', () => {
      // Error is always followed by close; let the close handler drive reconnect
    });
  }

  connect();

  return {
    send: (data: unknown) => ws?.send(JSON.stringify(data)),
    close: () => { stopped = true; ws?.close(1000); },
  };
}
```

### Backoff schedule example (initialDelay=1s, maxDelay=30s)

| Attempt | Base delay | With jitter (approx) |
|---|---|---|
| 1 | 1 s | 1.0–1.3 s |
| 2 | 2 s | 2.0–2.6 s |
| 3 | 4 s | 4.0–5.2 s |
| 4 | 8 s | 8.0–10.4 s |
| 5 | 16 s | 16–20.8 s |
| 6+ | 30 s | 30–39 s (capped) |

## Full Example — Authenticated WebSocket Server with Broadcast

```typescript
import { WebSocketServer, WebSocket } from 'ws';
import { createServer } from 'http';
import { parse } from 'url';
import jwt from 'jsonwebtoken';
import { createClient } from 'redis';

// ─── Types ────────────────────────────────────────────────────────────────────

interface AuthenticatedSocket extends WebSocket {
  id: string;
  userId?: string;
  isAlive: boolean;
  pingTimeout?: ReturnType<typeof setTimeout>;
}

interface ClientMessage {
  type: 'auth' | 'message' | 'pong';
  token?: string;
  payload?: unknown;
}

// ─── Redis setup ──────────────────────────────────────────────────────────────

const pub = createClient({ url: process.env.REDIS_URL ?? 'redis://localhost:6379' });
const sub = createClient({ url: process.env.REDIS_URL ?? 'redis://localhost:6379' });

await pub.connect();
await sub.connect();

// ─── Local client registry ────────────────────────────────────────────────────

const clients = new Map<string, AuthenticatedSocket>();

// ─── HTTP + WebSocket server ──────────────────────────────────────────────────

const httpServer = createServer();
const wss = new WebSocketServer({ server: httpServer });

// ─── Redis broadcast subscription ────────────────────────────────────────────

await sub.subscribe('global:broadcast', (raw) => {
  for (const ws of clients.values()) {
    if (ws.readyState === WebSocket.OPEN && ws.userId) {
      ws.send(raw);
    }
  }
});

// ─── Heartbeat interval ───────────────────────────────────────────────────────

const PING_INTERVAL = 30_000;
const PONG_TIMEOUT  = 10_000;

const heartbeatInterval = setInterval(() => {
  for (const ws of clients.values()) {
    if (!ws.isAlive) {
      ws.terminate();
      continue;
    }
    ws.isAlive = false;
    ws.ping();
    ws.pingTimeout = setTimeout(() => ws.terminate(), PONG_TIMEOUT);
  }
}, PING_INTERVAL);

wss.on('close', () => clearInterval(heartbeatInterval));

// ─── Connection handler ───────────────────────────────────────────────────────

wss.on('connection', (rawWs: WebSocket, req) => {
  const ws = rawWs as AuthenticatedSocket;
  ws.id = crypto.randomUUID();
  ws.isAlive = true;
  clients.set(ws.id, ws);

  let authenticated = false;
  const authTimeout = setTimeout(() => {
    if (!authenticated) ws.close(4001, 'Authentication timeout');
  }, 5_000);

  // Handle RFC 6455 pong frames (for heartbeat)
  ws.on('pong', () => {
    ws.isAlive = true;
    clearTimeout(ws.pingTimeout);
  });

  ws.on('message', async (data) => {
    let msg: ClientMessage;
    try {
      msg = JSON.parse(data.toString());
    } catch {
      ws.close(4000, 'Invalid JSON');
      return;
    }

    // ── Authentication phase ─────────────────────────────────────────────────
    if (!authenticated) {
      if (msg.type !== 'auth' || !msg.token) {
        ws.close(4003, 'Send auth message first');
        return;
      }

      try {
        const payload = jwt.verify(msg.token, process.env.JWT_SECRET!) as { sub: string };
        ws.userId = payload.sub;
        authenticated = true;
        clearTimeout(authTimeout);

        ws.send(JSON.stringify({ type: 'auth_ok', userId: ws.userId }));
        console.log(`Client ${ws.id} authenticated as user ${ws.userId}`);
      } catch {
        ws.close(4002, 'Invalid or expired token');
      }
      return;
    }

    // ── Authenticated message handling ───────────────────────────────────────
    if (msg.type === 'message') {
      const envelope = JSON.stringify({
        fromUserId: ws.userId,
        payload: msg.payload,
        timestamp: Date.now(),
      });

      // Publish to Redis — all instances will broadcast to their local clients
      await pub.publish('global:broadcast', envelope);
    }
  });

  ws.on('close', (code, reason) => {
    clearTimeout(authTimeout);
    clearTimeout(ws.pingTimeout);
    clients.delete(ws.id);
    console.log(`Client ${ws.id} disconnected: ${code} ${reason.toString()}`);
  });

  ws.on('error', (err) => {
    console.error(`WebSocket error on client ${ws.id}:`, err.message);
  });
});

// ─── Start ────────────────────────────────────────────────────────────────────

httpServer.listen(3000, () => {
  console.log('WebSocket server listening on :3000');
});

// ─── Graceful shutdown ────────────────────────────────────────────────────────

process.on('SIGTERM', async () => {
  console.log('Shutting down...');
  for (const ws of clients.values()) {
    ws.close(1001, 'Server going away');
  }
  wss.close();
  await pub.quit();
  await sub.quit();
  process.exit(0);
});
```

## Quick Reference

| Concept | Key point |
|---|---|
| Upgrade handshake | HTTP 101, `Sec-WebSocket-Accept` = base64(SHA1(key + GUID)) |
| Frame overhead | 2 bytes minimum vs ~800 bytes HTTP headers |
| Close codes | 1000=normal, 1006=abnormal (no close frame), 4000-4999=app-defined |
| Scaling | Redis pub/sub for cross-instance broadcast; sticky sessions alone are insufficient |
| Heartbeat | Server pings every 30 s; terminate if no pong within 10 s |
| Auth | Query param (short-lived tokens only) or first message with timeout |
| Reconnect | Exponential backoff with jitter; do not reconnect on code 1000 |
