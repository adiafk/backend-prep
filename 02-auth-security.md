# 02 — Authentication & Security

## Authentication vs Authorization

Authentication answers **who are you?** Authorization answers **what are you allowed to do?**

A backend should authenticate first and then authorize the requested resource/action.

---

## JWT

JWT is a signed token format commonly used to carry claims:

```text
base64url(header).base64url(payload).base64url(signature)
```

A signed JWT is not encrypted. Anyone holding the token can normally decode its payload.

Know:

- issuer (`iss`)
- audience (`aud`)
- expiry (`exp`)
- signing keys
- key rotation
- access vs refresh tokens
- revocation strategy

## Sessions vs JWT

### Server session

```text
Client cookie -> session ID -> server/session store
```

The server owns the state.

### JWT

```text
Client -> signed claims -> server verifies signature
```

JWT can reduce server-side session lookup for access tokens, but revocation and token lifecycle become important.

Do not answer "JWT is always better". Discuss requirements.

---

## Refresh-token rotation

A strong flow is:

```text
Login
 -> access token
 -> refresh token

Refresh
 -> validate old refresh token
 -> rotate it
 -> issue new pair
 -> invalidate previous token
```

If reuse of a rotated token is detected, invalidate the relevant token family/session.

## OAuth 2.0 and PKCE

OAuth is an authorization framework. OpenID Connect builds identity information on top of OAuth.

PKCE protects authorization-code flows, especially public clients, by binding the authorization request to a secret generated by the client.

Flow:

```text
Client creates code_verifier
       |
code_challenge sent to authorization server
       |
User authenticates
       |
authorization code returned
       |
Client sends code + verifier
       |
Server checks verifier against challenge
       |
Tokens issued
```

Know redirect URIs, scopes, authorization codes, access tokens, refresh tokens, and state/CSRF protection.

## Hashing vs Encryption vs Encoding

- Encoding changes representation; it is not security.
- Encryption is reversible with the correct key.
- Hashing is one-way and useful for integrity and password verification.

Passwords should use slow password-hashing algorithms such as Argon2, bcrypt, or scrypt with salts rather than raw SHA-256.

## Cookies

Know:

- HttpOnly
- Secure
- SameSite
- expiration
- domain/path
- CSRF implications

HttpOnly helps prevent JavaScript from reading a cookie, while Secure restricts transmission to HTTPS.

## Rate Limiting

Common algorithms:

- fixed window
- sliding window
- token bucket
- leaky bucket

Token bucket models a bucket that refills at a configured rate and allows bursts up to the bucket capacity.

### Common interview traps

- Authentication is not authorization.
- CORS is not authentication.
- JWT payloads are not automatically confidential.
- Client-side authorization checks cannot replace server-side authorization.
- A secret in frontend code is not a secret.
